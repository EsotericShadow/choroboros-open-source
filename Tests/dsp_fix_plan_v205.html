Phase 1 — NaN Guard Hardening (C6)

Phase 1 — UB Elimination

SAFETY Eliminates the only undefined behavior in the plugin. Zero behavior change for valid inputs — these guards only fire if upstream NaN propagation occurs (e.g., during a core crossfade glitch or numeric edge case).

The fix

Every manual-buffer core has a static_cast<int>(readPos) that is UB if readPos is NaN. Add a one-line sanitization before the cast. The pattern:

// BEFORE (UB if NaN):
int i0 = static_cast<int>(readPos);

// AFTER (defined behavior always):
if (!(readPos >= 0.0f)) readPos = 0.0f;  // Catches NaN (NaN fails all comparisons)
int i0 = static_cast<int>(readPos);

Using !(readPos >= 0.0f) instead of std::isnan() because it works correctly even with -ffast-math (which is S1 — std::isnan gets optimized away under -ffinite-math-only). A NaN fails the >= comparison, so the negation catches it.

Source/Cores/blue_engine_modern/ChorusCoreCubic.cpp — readCubic() line 92

Source/Cores/blue_engine_modern/ChorusCoreThiran.cpp — processDelay() line 208 (std::floor path)

PREDICTED OUTCOME

Benchmark: Identical results — NaN never reaches these paths in normal operation

Audio: Zero audible change

CPU: +1 branch per sample per core (~0.5 ns on M-series, completely negligible)

Safety: If a NaN ever does propagate (e.g., from a future bug in the LFO or smoothing chain), the plugin will read from buffer position 0 instead of invoking undefined behavior. The output will be wrong but defined — no crash, no memory corruption, no security vulnerability.

RISK

Extremely low. The guard is a single branch that never fires in normal operation. The only way to introduce a regression is if the readPos = 0.0f fallback produces a click when a NaN appears — but a NaN reaching this point already means audio is broken upstream, so producing buffer[0] instead of UB is strictly better.

Phase 2 — Thiran Ping-Pong Fix (S-NEW-B)

Phase 2 — Quality Fix

QUALITY This is the audible fix. The Thiran allpass's ping-pong aliasing comes from zeroing the allpass state on every integer-delay boundary crossing.

Root cause

At ChorusCoreThiran.cpp line 227: newActive.state.fill(0.0f) zeros the incoming allpass state whenever the integer delay changes. This creates a discontinuity that the 48-sample sin²/cos² crossfade must absorb. At fast LFO rates (high depth + high rate), boundaries cross frequently, and the 48-sample crossfade can't fully mask repeated zero-state transients. The result: scratchy, aliasing-like artifacts that sweep with the LFO.

The fix — two options (investigate both)

Option A: Copy state from fading allpass (preferred)

Instead of zeroing the new allpass state, copy the fading allpass's state as a starting point. The new coefficients are different (for the new integer delay), but the state values represent recent signal history that's a much better approximation than zero.

// BEFORE:
newActive.state.fill(0.0f);
computeCoefficients(thiranD, newActive.a);

// AFTER:
newActive.state = fadingAp.state;  // Warm start from fading state
computeCoefficients(thiranD, newActive.a);

Where fadingAp is the allpass instance that was just active (before the swap). Need to capture this reference before thiranCh.aIsActive flips.

Option B: Extend crossfade length

If state copying introduces instability (unlikely but possible with mismatched coefficients), increase XFADE_LENGTH from 48 to 128 or 256 samples. Longer crossfade = more masking at the cost of slightly softer transient response.

PREDICTED OUTCOME — Option A

Audio: Significant reduction in ping-pong aliasing artifacts. The allpass starts from a warm state that approximates recent signal, so the crossfade blends two similar signals instead of blending signal-with-zero. At slow LFO rates: improvement is subtle. At fast rates with high depth: dramatic improvement.

Benchmark: True peak numbers may change slightly (±0.1 dB) due to different transient shape during crossfades. Noise floor unchanged.

CPU: +5 float copies per boundary crossing (copying the 5-element state array). Boundary crossings happen at most once per sample. Negligible.

Stability risk: Low. The Thiran allpass is inherently stable (all poles inside unit circle) regardless of initial state. Mismatched coefficients with warm state may produce a brief (~5 sample) transient, but the crossfade masks it. Worst case is it sounds like a very short click that the 48-sample crossfade absorbs. If testing reveals instability, fall back to Option B.

PREDICTED OUTCOME — Option B (fallback)

Audio: Moderate improvement. Longer crossfade masks the zero-state transient better, but doesn't eliminate the root cause. At very fast modulation, artifacts are reduced but not gone.

CPU: More samples in dual-allpass mode per crossing. At XFADE_LENGTH=128: ~2× the crossfade CPU cost. Still small relative to the per-sample coefficient recompute.

Phase 3 — Cross-Channel Smoothing Fixes

Phase 3 — Stereo Precision

QUALITY STEREO Two cores share smoothing state across L/R channels, causing channel 1 to start with pre-smoothed values from channel 0's processing pass.

Fix A: Tape smoothedDepth

ChorusCoreTape.cpp — smoothedDepth is a single float member updated per-sample inside the channel loop. Channel 1 inherits channel 0's converged depth.

// BEFORE (single member):
float smoothedDepth = 0.0f;
// In processDelay, inside per-sample loop:
smoothedDepth = depthSmoothCoeff * smoothedDepth + ...

// AFTER (per-channel):
std::vector<float> smoothedDepth;  // sized in prepare()
// In processDelay:
smoothedDepth[ch] = depthSmoothCoeff * smoothedDepth[ch] + ...

Fix B: LinearEnsemble smoothedColour

ChorusCoreLinearEnsemble.cpp — Same pattern. smoothedColour is a single float updated per-sample, shared across channels. This is likely contributing to Black_HQ's -1.47 dB stereo imbalance in the benchmark.

// BEFORE:
float smoothedColour = 0.0f;

// AFTER:
std::array<float, 2> smoothedColour {{ 0.0f, 0.0f }};
// Per-sample: smoothedColour[ch] += alpha * (target - smoothedColour[ch]);

PREDICTED OUTCOME

Tape stereo balance: Should tighten from current value toward 0 dB during depth changes. Steady-state balance unaffected (both channels converge to same target).

Black_HQ stereo balance: The -1.47 dB imbalance should reduce significantly. The colour controls tap2Mix and secondTapDepthScale, so a shared smoother means channel 1 gets different tap weights during colour transitions. Making this per-channel should bring balance much closer to 0 dB.

Audio character: Subtle. During knob movements, L and R will now track identically instead of R lagging. For static knob positions: zero change.

CPU: +1 float per channel (trivial).
